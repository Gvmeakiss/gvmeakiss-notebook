# Windows 调优：实践 · 审计 · 证据 · 清单 · 游戏

这五份材料是同一件事的五个面：**怎么把一台 Windows 调到能用的状态，以及凭什么相信某个改动真的有效。**

它们原先分散在 `docs/` 和顶层 `game-optimizations/`，收进一个目录是因为**互相引用太多**：
证据决定清单，清单落成脚本，脚本由两次真机实践检验，实践又反过来改写证据。放在一起才看得见这条链。

## 按目的读，不按编号读

| 你的目的 | 路径 |

## 贯穿五份材料的四条纪律

1. **先测量再优化** —— 没有测量工具的"优化"结论不可信（`PresentMon` / `HWiNFO` / `LatencyMon`）
2. **只看结果，不看开关** —— 注册表值写对了、任务状态 Ready、界面打绿勾，都不等于功能真的生效
3. **能回滚才算做完** —— 还原点（粗粒度）+ 逐项撤销脚本（细粒度），缺一不可
4. **把自己的误判写下来** —— 02 里那 3 处误判、03 里对 RegBack 的修正，都是这条纪律的产物

## 维护约定

- **新增游戏** → `games/` 下加子目录，按 `games/README.md` 的模板写，并更新那里的索引表
- **新增证据** → 进 03，按「有测量 / 有机制无测量 / 机制就是错的」三档归档，必须带出处
- **新增核查项** → 进 04，同时在 `skills/win-ai-gaming-setup/scripts/verify-env.ps1` 里加对应检查，
  否则就是"只写了文档、没人执行"
- **发现误判** → 不要删旧结论，改成「原判断 → 新证据 → 修正」，02 与 03 都是这么写的

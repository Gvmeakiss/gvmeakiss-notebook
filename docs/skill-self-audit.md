# 如何审计一个 Skill：把"文档承诺"变成"可验证事实"

> 一个 skill 写的和它跑的可能不是同一件事。本文记录一次完整自审的**方法**，
> 包括 5 类真实缺陷、2 次性能优化，以及**我自己被基准测试证伪两次**的过程。
>
> 适用于任何"文档 + 脚本"形态的自动化项目，不限于 Windows。

## 1. 为什么要审"skill 自己"

这类项目的价值全在**承诺**上：`README` 说"跑完是 49 项验收"、"`-WhatIf` 什么都不改"、
"失败会返回非 0"。只要其中一条不成立，用户拿到的就是**一个和文档不同的程序**，
而且是**静默地**不同 —— 这比直接报错危险得多。

一条判据贯穿全文：

> **文档里的每一个承诺，都要能在代码里指出"哪一行强制了它"；
> 指不出来，就说明它只是一句愿望。**

本次审计就是这样找出 5 类缺陷的。

## 2. 安全实跑矩阵

审计的第一步不是读代码，而是**尽可能把每个入口用"不会改系统"的方式跑一遍**。
先给脚本分类，再决定怎么跑：

| 脚本能力 | 安全跑法 | 能否直接跑 |
|---|---|---|
| 纯只读（枚举、报告） | 直接跑 | ✅ |
| 有写入，且声明 `SupportsShouldProcess` | `-WhatIf` | ⚠ 见下节陷阱 |
| 有写入，**未**声明 `SupportsShouldProcess` | 只能读代码 / 指向临时目录 | ❌ 不要跑 |
| 需要必填参数 | 不传参数，看退出码与报错是否合理 | ✅（预期非 0） |

先做一次静态"副作用面"扫描，比逐个试快得多：

```powershell
# 每个脚本声明了什么能力
Get-ChildItem scripts -Filter *.ps1 | ForEach-Object {
    $raw = Get-Content $_ -Raw
    [pscustomobject]@{
        Script        = $_.Name
        CmdletBinding = [bool]($raw -match '\[CmdletBinding')
        WhatIf        = [bool]($raw -match 'SupportsShouldProcess')
        WritesReg     = [bool]($raw -match 'Set-ItemProperty|reg add|reg import')
        TouchesSvc    = [bool]($raw -match 'Set-Service|sc\.exe config')
        TouchesDev    = [bool]($raw -match 'pnputil|Disable-PnpDevice')
    }
}
```

**这一步立刻暴露了两个问题**：3 个脚本在任何 `-WhatIf` 下都返回非 0（看起来"预览不可用"），
其中 2 个其实是"缺必填参数"的**正确**行为 —— 所以**先分清"设计如此"与"真的有病"**。

## 3. 五类真实缺陷

以下每一类都在本次审计中实际发生，并附当时的判据。

### A. 描述与实际不符

| 实例 | 文档说 | 代码做 |
|---|---|---|
| 自动安装包管理器 | "`dev` 阶段会自动安装" | 实际在 **`check`** 阶段 |
| Markdown 编辑器 | "条件安装，先问用户" | **无条件安装** |
| 工具箱 | 列了 13 个脚本 | 实际 **14** 个 |

**判据**：把文档里的数字、阶段名、文件名逐个 grep 回代码，**对不上的就要改一边**。
数字最好由脚本产出（"实跑得到 49 项"）而不是手写死。

### B. 预览模式不可用或不可信

> 这一类**最危险**：用户以为只是看一眼，其实已经在改系统。

实例一：**前置依赖缺失导致硬退出**。
`-WhatIf` 在一台干净机器上、在打印任何计划动作**之前**就 `exit 1`（因为依赖没装）——
而 dry-run 恰恰是给新机器准备的。

实例二：**`-WhatIf` 不跨进程传递**。
主脚本用子进程调子脚本，参数里**没有** `-WhatIf`，于是：

| 命令 | 用户以为 | 实际 |
|---|---|---|
| `-Phase dev -WhatIf` | 只看计划 | **真的安装工具链** |
| `-Phase apps -WhatIf` | 只看计划 | **真的下载并安装软件** |
| `-Phase link -WhatIf` | 只看计划 | **真的写注册表关联** |

而横幅仍印着 `WhatIf: nothing will be changed`。

> **`-WhatIf` 是进程级偏好，不出本进程。每个跨进程调用都要自己转发。**

转发时**不能无脑加**：未声明 `SupportsShouldProcess` 的子脚本会因为多出该参数而绑定失败。
做法是**读子脚本源码判断它是否声明**，只对声明了的转发。

实例三：**预演路径自己造出假故障**。
`Set-Content` 本身支持 `-WhatIf`，所以临时文件没被创建；但紧随其后的外部工具
（`reg.exe import`）不受影响，于是导入一个不存在的文件，稳定打印
`FAIL ... Error opening the file`。同一问题的另一面：汇总写 `applied 0 change(s)`，
读起来像"没事可做"，真相是"23 项会改"。

**判据**：
- 预览必须能**走完全程**并列出"将会做什么"
- **判据看磁盘，不看输出文字** —— 指向全新临时目录，跑 `-WhatIf`，确认目录没被创建
- 预演分支要**自己算出"将会改多少"** 并说出来

### C. 退出码不反映结果

实例：一个脚本**完全没有 `exit` 语句**，只打印 `failures (N)` 就结束，
`$LASTEXITCODE` 永远是 0。而它的调用方**正是用退出码判定这一步成败** ——
一个装失败的环节被判为通过。

**判据**：凡是被编排层调用的脚本，结尾必须显式 `exit 0 / exit 1`。

### D. 判定逻辑自相矛盾

实例：诊断脚本第 1 段打印 `FAIL 服务缺失`，第 6 段却判 `everything looks healthy`。
根因：**"缺失"分支只打印、没有置同一个判定变量**，而后续 verdict 与修复逻辑都靠那个变量。
连带后果：`-Repair` 走到"没有被禁用，无需修复"然后**什么都不做**。

**判据**：每个失败分支都必须落到**同一个**判定变量上；并且"缺失"与"被禁用"是
**两种不同的失败模式**（修复手段不同）。

### E. 静默吞掉失败

实例：

```powershell
Invoke-Step 'check.ps1' @(...) 'baseline drift' | Out-Null
Record 'verify' ($a -and $b -and $c)      # ← 不含它
```

被调脚本对缺失输入会 `exit 1`，但返回值被 `Out-Null` 丢掉、又没进 `Record` ——
**失败既不出现在结果表，也不影响退出码**。用户看到 `verify PASS`，却有一项根本没跑。

**判据**：凡是"结果会决定成败"的调用，返回值必须同时进入 ① 可见输出 ② 退出码。
`Out-Null` 只能用于真正无关紧要的调用；缺前置数据时要**显式跳过并说明**。

## 4. 性能优化必须先证明"覆盖面等价"

这是本次最容易自我欺骗的环节。**我被自己的基准测试证伪了两次**，实录如下。

### 目标

把"枚举注册表里所有 `shell\open\command`"从 4.1 秒降下来。原实现是
`reg query /s` 全量导出（2.4 万行）再逐行解析。

### 第一版：声称快 138×，实际是**算少了**

改用 .NET `RegistryKey` **只下探一层**（`Classes\<ProgID>\shell\open\command`），
0.03 秒 vs 4.15 秒。但一致性核对发现：

```
仅原实现找到 : 90 条
```

那 90 条全是 **`Classes\Applications\<exe>\shell\open\command`** —— 我只走了一层，
把它们全漏了。**"更快"只是因为它干得少。**

### 第二版：补全了层级，但**大小写敏感**

把 `Applications` 子树也纳入，键名用哈希表比较。又缺 85 条：

```
AppX…\Shell\open\command     ← 大写 S
```

这个 hive 里 **`Shell` 与 `shell` 大小写混用**。原实现用 `-match`（默认不敏感）才没暴露；
我的键比较是大小写敏感的。

### 第三版：才发现原实现**自己**有数据错误

补上大小写不敏感后仍缺 85 条。单独验证其中一个键：

```
HKEY_CURRENT_USER\...\AppX<id>\Shell\open\command
    DelegateExecute    REG_SZ    {A56A841F-…}     ← 只有这个值，没有默认值
```

原实现的解析正则 `'REG_SZ\s+(.*)$'` **不检查值名**，于是把 `DelegateExecute` 的 GUID
**当成了命令行**读走（268 条里 85 条是这种形状）。

改用 `RegistryKey.GetValue('')` 读**真正的默认值** —— 这些键正确地返回"没有命令"。

### 结果

| | 原实现 | 最终 |
|---|---|---|
| 耗时 | 4.1 s | **0.4 s** |
| 条目 | 268 | 183（**更少，因为不再把 GUID 当命令行**） |
| 正确性 | 含 85 条伪造数据 | 干净 |

> **纪律：性能优化必须同时给出"更快"与"等价（或更正确）"两份证据。**
> 只报速度的优化，本质上是在赌。**差异必须逐条 diff，而不是比对总数。**

## 5. 环境缺陷 vs 代码缺陷

审计时很容易把"机器策略"记成"项目 bug"，反过来也会漏掉真 bug。本次遇到一个典型：

**现象**：`Windows PowerShell 5.1` 拒绝执行该目录**全部 14 个**脚本
（`cannot be loaded ... not digitally signed`），而 `pwsh` 14/14 正常。

**受控实验**（这一步是关键，不要跳过）：

| 同一份文件放在 | PS 5.1 `-File` |
|---|---|
| 项目目录（在 Desktop 下） | ❌ 拒绝 |
| 任意 Desktop 子目录 | ❌ 拒绝 |
| 用户 `%TEMP%` | ✅ 正常 |
| 用户主目录 | ✅ 正常 |

**变量只有一个：路径。** 再查机器：8 个代码完整性策略文件、强制模式开启。
结论：**机器策略限制，不是项目缺陷**（文件无"下载来源"标记、无签名要求）。

但它**有实践含义**：该项目的编排层在没装 `pwsh` 时会**静默降级到 5.1**，
在强策略机器上那一刻**全部子脚本都会失败**，而前置阶段可能已经报过成功。
⇒ 于是"装 PowerShell 7"从"体验优化"升级为**硬前提**，写进文档。

**判据：**
1. 先做**受控实验**（只改一个变量：路径 / 账号 / 宿主），再下结论
2. 环境问题也要问一句"它会不会改变项目的默认路径假设"
3. 明确写清"这不是项目 bug"，避免后来者重复排查

## 6. 把纪律变成工具，而不是写进文档

同一条纪律（"脚本必须 ASCII-only / 带 BOM"）在同一个项目里**被违反 4 次**，
包括**在刚讨论过它之后**、以及**由写文档的人自己**违反。

**结论不是"要更小心"，而是"检查必须脱离记忆"**。于是新增一个检查器：

```powershell
# 对目录下每个 .ps1：编码 + 双宿主解析（不执行，秒级）
pwsh -File scripts/check-script-hygiene.ps1

#   PASS  ASCII-only 或带 BOM，两宿主解析一致
#   WARN  非 ASCII 且无 BOM，但 5.1 恰好能解析（靠字节对齐的运气）
#   FAIL  两宿主分歧 ⇒ 计划任务必然以 0x1 静默失败
```

两个设计要点，都来自踩坑：

- **WARN 也要拦** —— "恰好能解析"依赖字节对齐，任何后续编辑都可能打破它
- **它必须能抓住作者自己** —— 实现后它当场抓住了我两次新引入的中文注释，
  所以被判据应该是"检查器在提交前挡下了吗"，而不是"我记得检查了吗"

**推广判据：**
> 一条纪律被违反第 2 次，就不该再加强措辞，而应该**写成一个可执行检查**，
> 并挂到验收流程里。

## 7. 验收清单（提 PR 前逐项过）

- [ ] 文档里的**每个数字**都能由脚本产出，而不是手写
- [ ] 文档里的**每个"可选 / 默认关闭 / 建议先问"**，代码里有对应开关强制
- [ ] 每个被编排层调用的脚本，**结尾显式 `exit 0/1`**
- [ ] 每个"结果会决定成败"的调用，返回值进入**可见输出 + 退出码**（不只 `Out-Null`）
- [ ] 每个失败分支落到**同一个**判定变量
- [ ] `-WhatIf` **能走完全程**，并转发给支持它的子脚本
- [ ] `-WhatIf` 的验收**看磁盘**，不看输出文字
- [ ] 性能优化同时给出**耗时**与**逐条差异**两份证据
- [ ] 每个脚本**双宿主**（PS 7 / PS 5.1）解析通过
- [ ] 脚本**纯 ASCII** 或带 BOM（由检查器验证，不靠记忆）
- [ ] 实际跑过**真实入口**至少一次（不是只跑子脚本）
- [ ] 环境相关结论有**受控实验**支撑，并标注"非项目缺陷"
- [ ] 脱敏扫描：无主机名 / 用户名 / 内网 IP / 设备型号 / 凭据

## 8. 脱敏声明

本文件不含真实主机名、用户名、内网 IP、设备型号或凭据。
示例中的 GUID、注册表路径、事件 ID 均为通用技术信息或占位值。

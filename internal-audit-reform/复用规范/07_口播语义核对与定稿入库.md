# 口播语义核对与定稿入库

本规范依据2026-10-20本轮口播修订确认的要求整理，适用于领导汇报和面向专业员工的流程宣导。目标是既能自然朗读，又不比有效材料多出业务要求。默认参照[口播撰写标准](../workflows/口播稿撰写标准.md)：正式、自然、完整、通顺，不把精炼变成极短句。

## 判断一句话能否保留

1. 找到材料明确表达的主体、动作、条件、范围、时点或关系。
2. 检查改写后是否改变要求强度，或让听众理解出额外义务。
3. 无直接依据、也非讲清要求所必需的解释，直接删去。
4. 缺失内容若影响必需要求的理解，单独向用户确认；不能先填成确定事实再要求用户纠错。

“符合工作常识”“听起来合理”“有助于衔接”都不能替代材料依据。删去不必要的解释后，仍可通过明确主语、调整句长、安排讲述顺序和简短转场改善听感。

## 本轮问题形成的核对规则

| 容易发生的扩写 | 应采用的标准 | 核对问题 |
| --- | --- | --- |
| 将发起人、接收人或发送节点的差异写成后续流程差异 | 分别说明材料明确的启动信息；统一管理关系按材料原意表达 | 是否暗示了两套后续流程？ |
| 将反馈期限扩展到审核审批 | 期限只对应材料明确的交付动作 | 是否多规定了谁必须何时完成？ |
| 用“才能、必须先”连接本来没有强制先后的内容 | 仅保留材料明确的依赖或先后 | 是否新设了前置条件？ |
| 为追踪、验收补充检查步骤、材料对应方法 | 只讲明文要求的检查内容和处理动作 | 是否替材料制定了操作细则？ |
| 用总结句扩大主体、范围或覆盖率 | 主体和适用环节连同数字一起保留 | 是否把局部要求写成全部主体都要做？ |
| 为降低AI感添加情景、故事或效果判断 | 用自然句式讲已有内容 | 是否增加了虚构事实或成效承诺？ |
| 只核对人名数字就宣布“没有新增” | 同时检查显性信息和整句话的隐含含义 | 听众会不会据此理解出新增要求？ |

这些规则不禁止“先、再、因此”等连接词，也不禁止自然转场、目的说明和有依据的归纳。材料明确存在先后或因果时可以使用；关键是关系有依据，不能新增义务或把作用表达成既成成效。

## 双向核对

- **材料到口播**：关键要求是否遗漏，条件、例外、主体和时限是否完整。
- **口播到材料**：每个业务判断是否有依据，连接语是否增添差异、步骤、义务或效果。
- **领导意见到表达**：名称符合实际工作；语言朴实；不造包装性新词；把要求讲清楚。
- **朗读检查**：直接讲业务，避免页面解说、反复预告、空泛总结和过长句；保持专业听众应有的信息密度。

只有确实取得并检查过的材料，才能写入核对结论。文本相同、文件哈希相同、排版正常属于文件检查，不能用来证明业务含义没有扩写。

## 当前目录的定稿标准

- 业务来源、表达样本和当前配套成品分开标记；用户认可的语言样本不自动成为新版业务配套定稿。正式配套稿使用稳定文件名，Word与Markdown同步；项目README直接说明用途和状态。
- 核对结果单独保存，不放入口播正文。未确认内容不得混入正式可念稿。
- 对话内容整理为最终确认事项和适用边界，不把反复试写的原始聊天当作制作规范。
- 出现问题后，修订原规范及示例，避免新增说明与旧规则互相矛盾。
- 被替代稿不列为并列默认版本。为本轮比较保留的AI旧稿明确标注“对照”，其余被替代过程稿通过Git历史追溯；不改写或强推既有历史。
- 可编辑PPT或海报若仅保留作视觉与制作参考，标清用途；不能让旧视觉样例成为现行业务口径。
- 提交前检查入口链接、版本说明、Word/Markdown一致性及最终排版，不混入渲染缓存、临时文件或无关资料。

## 可复制的复检指令

> 请逐段对照本次有效PPT和用户已确认的补充口径。先查遗漏，再检查每句是否暗示了未经确认的流程差异、前置条件、时限、职责、操作细则或效果。不得用工作常识补定规则。无直接依据且非必要的解释删去；影响必需要求理解的缺口另行确认。保留专业、自然、朴实的口播，避免页面解说、虚构案例和概念教学。最后同步覆盖现行稿、复用规范与入口，旧稿只留在Git历史中。
